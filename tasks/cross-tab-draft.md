## Step 2 contract — 2026-11-11

Baseline: clean `dev` at `32c8665`; candidate reports the preceding refactor committed/pushed. Step 2 is additive BFF infrastructure; the existing UI and legacy POST stay unchanged until separately authorised step 3. Candidate requests desktop-only browser verification.

- POST `/api/session-save-operations`: validated `{ operation_id: UUID, client_id: UUID, draft_id: nonempty bounded string, revision: nonnegative safe integer, session: CreateSession }`. Admit synchronously before starting one upstream call. Return 202 while pending, 200 for a retained terminal result, with `Location` and `Cache-Control: no-store`.
- GET `/api/session-save-operations/[id]`: 200 snapshot or 404 unknown; invalid IDs return 400. Every response identifies the current runtime. Snapshots retain operation/client/draft/revision and pending, succeeded (session) or failed (sanitised BFF error plus HTTP status) state.
- Same operation ID and canonical request joins/replays the original result, including failure. Reusing an ID with different content returns 409. A different operation for a pending or successfully saved draft within the same client returns 409 with the existing snapshot; a failed draft may start a fresh operation ID. No automatic upstream retries. Step 3 must persist one random client UUID shared by its tabs; the client namespace prevents unrelated browsers with `initial`/`legacy` draft IDs blocking each other.
- The process owns work independently of browser disconnection. Registry capacity is 1000 operations with no time eviction: reject new admissions with 503 at capacity, retaining all known results. Existing IDs remain readable/replayable. A restart or another instance has a different runtime ID and no record; unknown must never mean safe-to-retry automatically. This is deliberately single-process memory, not durable idempotency.
- Preserve supplied API/catalogue and upstream validation/error semantics. As agreed, uncertainty between BFF and mock API remains outside the exercise model. No cross-tab banners, browser save restrictions or UI protocol integration in this step.

## Step 3 contract and implementation — 2026-11-11

Baseline: clean `dev` at `ae7c08a`, reported committed/pushed by the candidate. Step 3 is authorised with the same desktop-only verification strategy. Supplied API/catalogue, dependencies and deployment remain unchanged.

- Extend the validated version-2 browser envelope with an optional persistent client UUID and save reservation (canonical request, expected runtime, start time, validated result or uncertainty). Reserve under the existing short draft Web Lock after queued edits settle; reject a submitted snapshot if the latest draft changed. Persist before sending. No API save is attempted without writable shared storage and Web Locks.
- The same atomic record gates every draft mutation. Buttons and name/headset fields reflect read-only state in catalogue cards, video details, draft composition and finalisation; filters/navigation/metadata retry remain available. Pending/uncertain drafts cannot be cleared or resubmitted. Existing failure retains authored values and unlocks; success atomically starts an empty new draft with a new identity exactly once. Wrong-runtime/operation/client/draft/revision and obsolete terminal responses cannot clear its successor.
- GET `/api/session-save-operations` supplies a no-store runtime handshake. POST accepts optional `expected_runtime_id` (always supplied by the new UI) and rejects a changed runtime before admission. This is necessary to safely resume a persisted-but-not-yet-admitted request after tab closure without duplicating it across a server restart. Existing infrastructure callers remain compatible.
- A browser-only shell island starts recovery on every route, independent of the submitting dialog. Poll the original operation; only a same-runtime unknown result may submit/replay the original request and ID. Browser transport has a 10-second timeout. Focus/online events also trigger checks; no new operation is invented after a lost response. Confirmed failure requires an explicit user retry with a fresh operation ID. Recovery polling is once per second per open page, with one in-flight check per page.
- Top-of-page banners are repeated inside native modal surfaces so their inert background does not hide status. Existing primary/destructive/success semantics cover pending/failure/success. Add only `--amber-800`, `--warning`/`--warning-foreground` and Tailwind semantic mappings for delays (8 seconds) or uncertainty. Copy is French and includes text status, links and manual checking; color alone conveys nothing.
- A lost runtime keeps the draft read-only and never causes automatic resubmission. After checking Mes séances, the user may explicitly confirm manual recovery, acknowledging the possible duplicate. This preserves the draft under a new identity and discards only its old tracking. Transient network uncertainty cannot use this escape; delayed outcomes from abandoned tracking cannot clear the recovered draft. Storage loss prevents submission/clearing; a storage warning asks for recovery/reload.
- Finalisation receives the coordinated save as an explicit dependency. Its existing validation/error tests inject the legacy API function as their transport fixture; the production UI exclusively uses the coordinator.
